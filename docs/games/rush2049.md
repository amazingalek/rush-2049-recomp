# San Francisco Rush 2049 (N64)

Status (2026-10-10): **playable.** Boots, menus and races run at full speed: a full three-lap race to the results
screen in a 10-minute run with no crash and a flat working set (433–435 MB), and the race timer keeps pace with the
wall clock. It runs at 60 fps by default (Graphics tab, "Game Frame Rate"), and 3D widens to the window's aspect
ratio, with the HUD moved to the edges and menu and HUD text upscaled. MusyX audio plays and Controller Pak saves
survive a restart. Single Race, Circuit, Ghost Race and Stunt all run, and all six race tracks race without a crash
(tracks 5 and 6 unlocked with the in-game cheat menu, see below). Multiplayer, tested with `--players`: two-player split screen (race, Practice, Battle) and four-player Stunt
render correctly. Ghost Race runs a full timed session through to the results and the Best Ghosts table, and the
translucent respawning car renders. Playing as a pak player (not JUST PLAY), a Ghost Race session writes the pak,
and after a restart the profile still remembers the last mode picked. Not yet seen: the ghost car itself. It was
behind the camera on lap 2, and it wasn't beside the car at the start of a Ghost Race in the next session. Whether
the game shows a saved ghost from lap 1 is unknown. Also not exercised: multiplayer with real second pads.

Testing tip: the cheat menu works and unlocks everything without playing through Circuit. On the main menu, highlight
OPTIONS and press L+R+Z+C-Up+C-Right together (keyboard: E+R+Q+T+H) until CHEATS appears; open it with A
(Space; Enter is Start, which always starts the game). Highlight ALL TRACKS, hold L+R and press Z with C-Up+C-Right,
C-Down+C-Left, C-Left+C-Up, C-Down+C-Right in turn (C buttons first, then Z), then press right to switch it ON.

## Building and running

Needs the toolchain from [../03-local-env.md](../03-local-env.md) (`tools/env.sh` puts clang-cl, CMake, Ninja,
N64Recomp and RSPRecomp in reach) and a Python venv at `.venv` with `spimdisasm`, `rabbitizer` and `numpy`.
From the repo root, in MSYS2 bash:

```sh
git submodule update --init --recursive
bash tools/rush2049/apply_runtime_patches.sh            # runtime submodule fixes, see "Runtime notes"
git clone https://github.com/shygoo/n64sym ref/n64sym    # signature list for gen_syms.py (MIT); ref/ is ignored
.venv/Scripts/python -I tools/rush2049/extract.py "<path to Rush 2049 (U) [!].z64>"
                                                         # writes roms/rush2049.us.z64 and roms/rush2049.us.recomp.z64
source tools/env.sh
cmake -S rush2049 -B rush2049/build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
      -DCMAKE_C_COMPILER=clang-cl -DCMAKE_CXX_COMPILER=clang-cl
bash tools/rush2049/iterate.sh 30                        # symbols, N64Recomp, RSPRecomp, build, 30 s boot test
```

`iterate.sh` regenerates `syms/rush2049/rush2049.us.syms.toml`, reruns N64Recomp into `rush2049/RecompiledFuncs/`,
generates `rush2049/rsp/musyx.cpp` once, builds, and boots the game for the given number of seconds with its log in
`rush2049/run.log`; `--no-recomp` as the second argument skips the first two steps. Afterwards
`ninja -C rush2049/build Rush2049Recompiled` is enough for source changes. Run `rush2049/build/Rush2049Recompiled.exe`
from `rush2049/` and pick the ROM (`roms/rush2049.us.z64`) in the launcher; the runtime checks its hash. Saves go to
`rush2049/saves/`.

## Triage (`py -3 -I tools/rom_triage.py <rom>`)

- **Graphics ucode: `RSP Gfx ucode F3DEX.NoN fifo 2.08 Yoshitaka Yasumoto 1999 Nintendo.`** This
  is F3DEX2 2.08 NoN `.fifo`, which is in RT64's supported table (see
  [../01-toolchain.md](../01-toolchain.md#3-rt64)). The biggest blocker class is cleared.
- **The triage's "no compression" was wrong.** No Yaz0/Yay0/MIO0/gzip magics, but the main code and both
  overlays are **raw deflate** streams (zlib `wbits=-15`, no header), which have no magic to find. Only the
  boot segment is plain.
- **Audio is MusyX v1** (Factor 5), not libultra's audio library: the RSP string `N64 RSP mixer V1.1` sits in
  boot data at `0x8002D890`. The triage tool only looks for libultra audio strings.

## Memory map

| Segment | ROM (original) | Recomp ROM | VRAM | Text size | Notes |
|---|---|---|---|---|---|
| boot | `0x1000` (plain) | `0x1000` | `0x80000400` | `0x80027DD0` end | Game boot code, libultra 2.0J, MusyX CPU side. |
| boot ucode text | | | `0x80027DD0`–`0x8002C5E0` | | rspboot, F3DEX2, MusyX mixer text linked into `.text`. **Not CPU code.** |
| boot_tail | | `0x2D1E0` | `0x8002C5E0` | `0x1C` | One CPU function after the ucode text: a `cache 0x0D` loop. Stubbed. |
| main | `0xB0CB10` (deflate) | `0x01000000` | `0x80086A50` | `0x89330` (to `0x8010FD80`) | Inflated at boot. Data follows to `0x801249F0`, bss to `0x8017A640`. |
| ovl1 | `0xB5C534` (deflate) | `0x010A0000` | `0x8038A400` | `0x25580` (to `0x803AF980`) | |
| ovl2 | `0xB6FEC4` (deflate) | `0x010D0000` | `0x8038A400` | `0x9740` (to `0x80393B40`) | Shares VRAM with ovl1; probably the battle overlay. |

- **Boot.** The entry clears bss at `0x8002E8E0` (size `0x58170`), sets `sp = 0x80086A50` and jumps to
  `0x800020F0`.
- **Inflate.** `func_80006814(rom, dst, flag)` inflates a raw deflate stream from cart ROM to `dst` and returns
  the size. The main thread calls it at `0x80002334` with `(0xB0CB10, 0x80086A50, 0)`; the wrapper
  `func_800026C0` calls it at `0x800026F4` for everything else. After inflating it runs `osInvalICache` over
  the output, which is where the runtime registers the code (`rush2049/src/code_loading.cpp`).
- **Overlays.** A table of their ROM addresses is at `0x8002B020` (`{0xB5C534, 0xB6FEC4}`). `func_800A11E4`
  loads them: table[0] from `0x800A1384` and `0x800C9040`, table[1] from `0x800A128C`. Both go to
  `0x8038A400`.
- `tools/rush2049/extract.py` writes `roms/rush2049.us.recomp.z64`: the original ROM padded to 16 MiB with the
  three inflated segments appended at the "Recomp ROM" addresses. N64Recomp reads code from there; the
  runtime loads the original ROM.

### Where the boot CPU text ends

libultra links the RSP microcode text into `.text`, after the CPU code. Decoded as MIPS, ucode looks like code
with `jal 0x84000xxx` targets and dense COP2 (`lwc2`/`swc2`/vector) ops. That mattered: a `jal 0x80001088` in
the ucode text split `func_80000FE8` in the middle and broke the first recompile. The first IMEM-range
`j`/`jal` in boot is at `0x80027DD0` (rspboot), and nothing in the CPU code calls past it except
`0x8002C5E0`.

## Function naming

`tools/rush2049/gen_syms.py` writes `syms/rush2049/rush2049.us.syms.toml`:

1. **Boundaries** from spimdisasm (`--function-info`), with false splits merged (a function that branches into
   the next one, which nothing calls).
2. **libultra names** from n64sym's signature list (MIT, `ref/n64sym`): CRC32 of the first 8 bytes and of the
   whole function, relocated fields masked. Matches that collide under several names are dropped, as are a
   few names that hit game code (`UNTRUSTED_NAMES`).
3. **Hand names** (`MANUAL_NAMES`) for what signatures can't see: `exceptasm.s` (`__osExceptionPreamble`,
   `__osException`, `send_mesg`, `handle_CpU`), the PI/SI access-queue pairs (identical code, different
   globals), and functions identified by their calls and registers (`viMgrMain`, `osEPiStartDma`,
   `osAiSetFrequency`, `osContInit`, …).
4. Optional per-game registry `syms/rush2049/names.toml` (`[[func]]` with `section`, `vram`, `name`).

Names matter to N64Recomp beyond readability: it drops or reimplements libultra functions **by name**, so an
unnamed libultra function that touches hardware gets recompiled and crashes, and a game function wrongly given
a libultra name silently disappears. `func_8000262C` (the game's lock release, `osSendMesg` on its own queue)
matched `__osSiRelAccess`'s signature from a debug libultra build and was being dropped that way.

`tools/rush2049/xmatch.py <other rom> <other syms>` compares unnamed boot functions with another game's
named ones by address-masked code. Against Rush 2 (`ref/rush2recompiled`'s symbol file, used as facts only)
it confirms the scheduler, `sprintf`, the inflate routines and a few libultra helpers.

## What N64Recomp can't translate

- **Speech decoder asm island, `0x800277D0`–`0x80027DD0`.** Hand-written GSM 06.10 full-rate decoding
  stages. The code reads the PC with `bltzal $zero`, calls local subroutines with `bal`, jumps through
  `jalr $t3` to per-section LAR interpolation stubs and keeps its tables inline (QLB `0CCD 2CCD 5333 7FFF`,
  the small-xmaxc table at `0x800278BC`). Entry points, all called from `func_800265xx`:
  - `0x800277D0`: APCM inverse quantization and RPE grid positioning (xmaxc, Mc, xMc[13], erp[40]).
  - `0x800278C4`: long-term synthesis (state, Ncr, bcr, erp). The lag is kept at state `+0x166` and only
    replaced when 40..120.
  - `0x80027B44`: short-term synthesis lattice and de-emphasis (0x6E14) over a 160-sample frame, with the
    LARpp sets at `+0x168`/`+0x178` picked by the halfword at `+0x188`, v[0..7] at `+0x140` and msr at
    `+0x164`. Output is clamped and masked with `0xFFF8`.

  They are `ignored` in `us.toml` and implemented in `src/gsm_decoder.cpp`, translated from the assembly
  rather than from the specification, so they keep its 32-bit arithmetic.

  **The decoder is dead code in this ROM.** Every path into it starts at a function nothing references, by
  `jal`, by a `lui`/`addiu` pair or as a pointer in ROM data: `800277D0` ← `80026360` ← `80026558` ←
  `80026640` (unreferenced) or `800268D0` ← `80025F74` ← `8002574C`, a stream callback that only
  `80025C68` (unreferenced) installs at `0x80038024`. The other entry points in `0x80025594`–`0x80026640` are
  unreferenced too. It is a linked-in streaming and speech library the game never uses. The translation stays
  so the island doesn't need a stub, and it logs `[gsm] first speech frame` if a path turns up after all.
- **`0x8002C5E0`**: `cache 0x0D` (create dirty exclusive) over a buffer. Meaningless on PC; stubbed.

## Runtime notes

- **Threads.** The game stops and restarts thread 5 (`func_800E7808`, struct `0x80034840`) from other threads.
  Upstream `osStopThread`/`osStartThread` on another thread corrupted the run queue, so
  `runtime-patches/N64ModernRuntime-0001-threads-and-ai-events.patch` fixes `thread_queue_remove` and makes
  a restarted thread go back into the message queue it was blocked on. `tools/rush2049/apply_runtime_patches.sh`
  applies the patches to the submodule (it skips ones already applied).
- **Busy-wait loops.** ultramodern runs one game thread at a time and only delivers VI/SP/DP/AI messages inside
  OS calls, so a loop polling memory another thread or an interrupt changes never ends. Every such loop gets a
  `yield_self_1ms` hook. `tools/rush2049/find_spins.py` lists the polling loops and `--toml` emits the hooks;
  the generated block sits between the markers in `us.toml`, and the audio thread's spin at `0x8008AB44` has
  its own hook.
- **Audio pacing.** The AI DMA thread (`func_80010A40`) waits for one `OS_EVENT_AI` per 0x300-byte buffer
  (192 stereo frames at 22050 Hz, about 115 per second). Upstream sends one per VI, which played audio at
  half speed; the runtime patch sends one per buffer's worth of audio played instead.
- **MusyX.** Audio tasks run through mupen64plus-rsp-hle's MusyX v1 HLE by default (`src/hle/`, vendored,
  GPL-2.0-or-later). `--musyx lle` runs the game's microcode through RSPRecomp instead (`rsp/musyx.cpp`,
  generated, not committed), and `--musyx compare` runs both on the same input every 25th task. They agree.
  The sample-address callback `func_8010FD60` turns addresses into cart KSEG1 addresses
  (`0xB0000000 | addr`), so the mixer DMAs samples straight from ROM.
- **Audio levels.** The mix wanders a lot: the per-second mean goes up to ±7000 and RMS reaches ~11000
  once the music builds. Project64 2.3 (LLE RSP, recorded through WASAPI loopback) shows the same thing, so it
  is the soundtrack and not a bug. The game's own mix clips too: both recordings have the same RMS (0.238)
  and about the same share of samples above 0.97 of full scale once resampled to 44.1 kHz (0.21% recomp,
  0.25% Project64). Project64's never go above 0.99, so its output path limits the peaks (likely the Windows
  shared-mode limiter), while the `--dump-audio` file holds the game's raw samples. Playback scales them by
  0.5 before SDL, so the recomp doesn't clip on output.
- **Controller Pak.** The game saves only to the Controller Pak (no EEPROM, SRAM or flash calls).
  `src/controller_pak.cpp` implements `osPfs*` over a 32 KiB `.mpk` image per port
  (`saves/controllerpak_<n>.mpk` under the config folder, the layout emulators use), and its definitions take
  the place of librecomp's no-pak stubs at link time. Every 30 frames the game queries the controllers
  (`func_800E73D8`), `func_800A43FC` turns status bit 0 into a "pak inserted" flag (per-port struct at
  `0x80144030`, stride `0x304`: `+1` handled, `+2` inserted, `+3` removed), and `func_800A377C` calls
  `osPfsInitPak`, then `osMotorInit` only if that fails. It compares each pak's 32-byte ID block across ports
  to spot a pak moved between controllers, so `osPfsInitPak` copies the image's ID block into `OSPfs.id`, and
  each port's pak is formatted with its own serial. In single-player mode only port 1 reports a controller.
- **Keyboard defaults.** The game's own CONTROLS screen: gas A, brake B, steer with the stick, shift up R, shift
  down C-Down, reverse C-Left, abort C-Up, view L. The frontend's stock keyboard defaults put the C buttons on the
  arrows, so Up aborted and Left reversed. `src/config.cpp` overrides them: the arrows are a second stick (steering
  and menus, like WASD), and the C buttons are T (up), F (left), G (down) and H (right). The rest are unchanged:
  Space A (gas), Left Shift B (brake), E L, R R, Q Z, Enter Start, I/J/K/L the D-pad.
- **Rumble Pak.** One accessory slot per controller, so the General tab has a "Controller Accessory" option
  (Controller Pak by default, or Rumble Pak). With Rumble Pak, `osPfsInitPak` fails with `PFS_ERR_DEVICE` (11),
  as libultra's ID check does on a Rumble Pak. `func_800A1E94` maps 10 and 11 to "not a Controller Pak", and then
  the game calls `osMotorInit`. It only trusts the result if `OSPfs.queue` was filled in, which libultra does
  before the ID check, so the failing path writes `queue` and `channel` too. Without that, the game reads the port
  as having no pak at all. Verified: the Player 1 screen shows RUMBLE PAK, the game starts the motor in a race
  (`[rumble] first motor start` in the log), and the `.mpk` is left untouched.
- **Frame rate.** The original draws at 30 fps: the scheduler swaps a finished frame only when the retrace count
  has moved by at least 2 since the last swap. That check (`sltiu $at, $t3, 2`) happens in two places, when the RDP
  finishes (`func_80000C54`, 0x80000CFC) and on retrace for a pending swap (`func_80000880`, 0x800008C8), and the
  next frame starts only after a swap. That is the whole cap. Game logic uses measured time (the RDP-done path keeps
  an `osGetTime` delta at 0x80124F70), so speed doesn't depend on frame rate. Measured at 60 fps, the race clock
  advanced 21.73 s over 21.77 s of wall time. The Graphics tab's "Game Frame Rate" option (60 FPS by default, or
  30 FPS Original) feeds `rush2049_frame_pace`, a hook before both checks that turns a delta of 1 into 2. Probes:
  about 300 RDP completions per 300 retraces at 60, and 150 at Original. Above 60 would need either a faster VI
  (audio is also paced by retrace) or RT64 interpolation, which needs matrix groups in the display lists.
- **Widescreen and resolution.** RT64 widens the 3D view at runtime (Graphics tab: Aspect Ratio Expand, the
  default) whenever the game's viewport spans the whole framebuffer, which covers single-player races and the
  attract demo. Menus are drawn 4:3 and stay pillarboxed, and so does split screen: its views are narrower than the
  screen, so RT64 leaves them 4:3. Resolution (Original, Original 2x, Auto) and MSAA are RT64's options on the same
  tab, and Auto renders at window resolution.
- **Widescreen HUD** (`src/widescreen.cpp`). The race HUD is texture rectangles at 4:3 positions, all drawn by
  `func_80087110(x0, y0, x1, y1, …)`, which appends `G_TEXRECT` + `G_RDPHALF_1` + `G_RDPHALF_2` at the display list
  pointer in 0x80149438. Hooks at its entry and its single exit (0x800877FC) rewrite that triple in place as RT64's
  `gEXTextureRectangle` (also 24 bytes) with a left origin for rects ending by x 58 (speedometer, gauge) or a right
  origin for rects starting from x 232 (lap, counters, minimap, timer). Centred messages stay put. Inserting a
  `gEXSetRectAlign` before the rect didn't work: callers keep their own copy of the display list pointer across the
  call and overwrite anything added. Two more patches go into each frame's list before the task starts (a hook in
  `func_80000E20` before `osSpTaskLoad`). The list's first command, `gsSPSegment(0, 0)`, is a no-op (segment 0 is
  never anything else), so it becomes `gEXEnable`, which RT64 needs in every list. The HUD's full-screen scissor
  would clip the moved rects to 4:3, and it follows a pipe sync, so the pair becomes a `gEXSetScissor` from the left
  edge to the right edge. All of this applies only in a single-player race. A race is when the timer
  (`func_8010761C`) was drawn in the last 8 retraces, and split screen is a frame whose top-level list sets a
  viewport narrower than 320. HUD Placement on the Graphics tab sets how far the HUD moves (Original keeps it 4:3).
  Not moved: the two spinning coin icons by the counters, which are 3D models. `--dump-dl <file> <seconds>`
  (`src/dl_dump.cpp`) writes a frame's display list as text and was how the HUD was found.
- **Hi-res font** (`src/hires_font.cpp`). Every font (menus, race HUD, messages) is a 4-bit intensity atlas 96
  texels wide, drawn as texture rectangles, so it is blocky at window resolution. The fonts come from the ROM, so no
  texture pack can ship in the repo: the game makes its own. Before each graphics task starts (the same
  `func_80000E20` hook), the display list is walked with a copy of RT64's load block TMEM emulation (a load tile or
  TLUT isn't emulated and marks TMEM unknown), and each intensity texture a `G_TEXRECT` or `gEXTextureRectangle` draws is hashed with
  `RT64::TMEMHasher` exactly as RT64 hashes it. A new hash is upscaled 4x (Catmull-Rom bicubic, then a contrast
  curve of 2.5 around half the atlas's peak: edges stay clean and the one-texel gaps inside glyphs stay open, which
  a threshold or Scale2x doesn't) and written as an RGBA8 DDS with mips to `hires_font/v1/` in the app folder, with
  an `rt64.json` listing them (shift `none`: `half` pulls slivers of neighbouring glyphs in). That folder is
  registered as a built-in pack below any user packs, through `recompui::renderer::set_builtin_texture_packs`, which
  `runtime-patches/RecompFrontend-0001-builtin-texture-packs.patch` adds. Only the first frame that draws a font
  shows the original; the pack persists across restarts, and bumping `pack_version` throws an old upscale away.
  Hi-res Font on the Graphics tab turns it off. Not affected: the seven-segment speedometer and odometer, which are
  colour textures. The generated pack is ROM-derived and must never be committed (`/rush2049/hires_font/` is
  ignored).
- **Expansion Pak.** The game checks for 8 MB and restricts content without it (some path objects and animated
  textures). The runtime reports 8 MB in `osMemSize`.
- **Prior art.** bryantmh/rush2recompiled (Rush 2, no license: facts only, no code) uses the same engine
  recipe: inflated segments at fake ROM addresses, a `load_overlays` hook after inflate, its own
  `osStartThread`/`osStopThread`, file-backed `osPfs*`, and yields inside busy-wait loops on the graphics task
  counter. Its port plan says a separate 2049 recomp would be the better route.
- **Decomp.** cabi24/SFRush2049-decomp targets the same SHA-1 (about 20% matched, no license, IDO 5.3
  `-mips2 -G0`).

## Developer flags

| Flag | Effect |
|---|---|
| `--boot` | Skip the launcher and start the game |
| `--stacks` | Every few seconds, print every game thread's stack and the probes |
| `--probes` | Print the probes only (scheduler messages, audio buffers, input reads, pak flags) |
| `--dump-audio <wav>` | Write everything sent to the audio device to a WAV file |
| `--dump-dl <file> <seconds>` | Write the first display list submitted after that many seconds, decoded as text (F3DEX2) |
| `--musyx hle\|lle\|compare` | Pick the MusyX implementation (default `hle`) |
| `--watch <hexaddr>` | Watch one RDRAM byte; print every thread's stack on each of its first 6 changes |
| `--players <n>` | Report ports 1..n as connected so the game offers n players with one pad; the extra ports get the same input as port 1 |
