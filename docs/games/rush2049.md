## Triage (`py -3 -I tools/rom_triage.py <rom>`)

- **Graphics ucode: `RSP Gfx ucode F3DEX.NoN fifo 2.08 Yoshitaka Yasumoto 1999 Nintendo.`** This
  is F3DEX2 2.08 NoN `.fifo`, which is in RT64's supported table (see
  [../01-toolchain.md](../01-toolchain.md#3-rt64)). The biggest blocker class is cleared.
- **The triage's "no compression" was wrong.** No Yaz0/Yay0/MIO0/gzip magics, but the main code and both
  overlays are **raw deflate** streams (zlib `wbits=-15`, no header), which have no magic to find. Only the
  boot segment is plain.
- **Audio is MusyX v1** (Factor 5), not libultra's audio library: the RSP string `N64 RSP mixer V1.1` sits in
  boot data at `0x8002D890`. The triage tool only looks for libultra audio strings.

- **Boot.** The entry clears bss at `0x8002E8E0` (size `0x58170`), sets `sp = 0x80086A50` and jumps to
  `0x800020F0`.
- **Inflate.** `func_80006814(rom, dst, flag)` inflates a raw deflate stream from cart ROM to `dst` and returns
  the size. The main thread calls it at `0x80002334` with `(0xB0CB10, 0x80086A50, 0)`; the wrapper
  `func_800026C0` calls it at `0x800026F4` for everything else. After inflating it runs `osInvalICache` over
  the output, which is where the runtime registers the code (`rush2049/src/code_loading.cpp`).
- **Overlays.** A table of their ROM addresses is at `0x8002B020` (`{0xB5C534, 0xB6FEC4}`). `func_800A11E4`
  loads them: table[0] from `0x800A1384` and `0x800C9040`, table[1] from `0x800A128C`. Both go to
  `0x8038A400`.
- `tools/rush2049/extract.py` writes `roms/rush2049.us.recomp.z64`: the original ROM padded to 16 MiB with the
  three inflated segments appended at the "Recomp ROM" addresses. N64Recomp reads code from there; the
  runtime loads the original ROM.

### Where the boot CPU text ends

libultra links the RSP microcode text into `.text`, after the CPU code. Decoded as MIPS, ucode looks like code
with `jal 0x84000xxx` targets and dense COP2 (`lwc2`/`swc2`/vector) ops. That mattered: a `jal 0x80001088` in
the ucode text split `func_80000FE8` in the middle and broke the first recompile. The first IMEM-range
`j`/`jal` in boot is at `0x80027DD0` (rspboot), and nothing in the CPU code calls past it except
`0x8002C5E0`.

## Function naming

`tools/rush2049/gen_syms.py` writes `syms/rush2049/rush2049.us.syms.toml`:

1. **Boundaries** from spimdisasm (`--function-info`), with false splits merged (a function that branches into
   the next one, which nothing calls).
2. **libultra names** from n64sym's signature list (MIT, `ref/n64sym`): CRC32 of the first 8 bytes and of the
   whole function, relocated fields masked. Matches that collide under several names are dropped, as are a
   few names that hit game code (`UNTRUSTED_NAMES`).
3. **Hand names** (`MANUAL_NAMES`) for what signatures can't see: `exceptasm.s` (`__osExceptionPreamble`,
   `__osException`, `send_mesg`, `handle_CpU`), the PI/SI access-queue pairs (identical code, different
   globals), and functions identified by their calls and registers (`viMgrMain`, `osEPiStartDma`,
   `osAiSetFrequency`, `osContInit`, …).
4. Optional per-game registry `syms/rush2049/names.toml` (`[[func]]` with `section`, `vram`, `name`).

Names matter to N64Recomp beyond readability: it drops or reimplements libultra functions **by name**, so an
unnamed libultra function that touches hardware gets recompiled and crashes, and a game function wrongly given
a libultra name silently disappears. `func_8000262C` (the game's lock release, `osSendMesg` on its own queue)
matched `__osSiRelAccess`'s signature from a debug libultra build and was being dropped that way.

`tools/rush2049/xmatch.py <other rom> <other syms>` compares unnamed boot functions with another game's
named ones by address-masked code. Against Rush 2 (`ref/rush2recompiled`'s symbol file, used as facts only)
it confirms the scheduler, `sprintf`, the inflate routines and a few libultra helpers.

## What N64Recomp can't translate

- **DSP asm island, `0x800277D0`–`0x80027DD0`.** Hand-written code that reads the PC with `bltzal $zero`,
  calls local subroutines with `bal`, jumps through `jalr` tables and keeps Q15 coefficient tables
  (`0CCD 2CCD 5333 7FFF`, …) inline. Three entry points are called from `func_800265xx`: `0x800277D0`,
  `0x800278C4` (clamps a delay at `+0x166` to 40..120 halfwords, shifts a 0x78-entry history buffer, then
  multiplies by a Q15 coefficient with rounding) and `0x80027B44`. They are stubbed (`us.toml`) and need C
  reimplementations. They look like audio effects on the CPU side.
- **`0x8002C5E0`**: `cache 0x0D` (create dirty exclusive) over a buffer. Meaningless on PC; stubbed.

## Runtime notes

- **Controller Pak.** The game saves only to the Controller Pak. N64ModernRuntime's `osPfs*` all return
  `PFS_ERR_NOPACK`, so a file-backed implementation is needed for saves.
- **Expansion Pak.** The game checks for 8 MB and restricts content without it (some path objects and animated
  textures). The runtime reports 8 MB in `osMemSize`.
- **MusyX audio.** The RSP mixer is not handled yet; audio tasks complete as silence. The sample-address
  callback `func_8010FD60` (reached through a pointer at `0x80038014`) turns addresses into cart KSEG1
  addresses (`0xB0000000 | addr`), so the mixer may DMA samples straight from ROM. Options: RSPRecomp on the
  MusyX ucode, or an HLE mixer (mupen64plus-rsp-hle's `musyx.c` is a reference).
- **Prior art.** bryantmh/rush2recompiled (Rush 2, no license: facts only, no code) uses the same engine
  recipe: inflated segments at fake ROM addresses, a `load_overlays` hook after inflate, its own
  `osStartThread`/`osStopThread`, file-backed `osPfs*`, and yields inside busy-wait loops on the graphics task
  counter. Its port plan says a separate 2049 recomp would be the better route.
- **Decomp.** cabi24/SFRush2049-decomp targets the same SHA-1 (about 20% matched, no license, IDO 5.3
  `-mips2 -G0`).
