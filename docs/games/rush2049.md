# San Francisco Rush 2049 (N64)

Status (2026-10-10): **playable.** Boots, menus and races run at full speed: a full three-lap race to the
results screen in a 10-minute run with no crash and a flat working set (433–435 MB), and the race timer keeps
pace with the wall clock. It runs at 60 fps by default (Graphics tab, "Game Frame Rate"; Match Framerate goes
higher), and 3D widens to the window's aspect ratio, split screen included, with the HUD moved to the edges, the
menu background carried out to the window's edges, and menu and HUD text upscaled. MusyX audio plays and Controller Pak saves survive a restart. Single Race, Circuit, Ghost Race and
Stunt all run, and all six race tracks race without a crash (tracks 5 and 6 unlocked with the in-game cheat
menu, see below). Multiplayer, tested with `--players`: two-player split screen (race, Practice, Stunt, Battle)
and four-player Stunt and Battle render correctly, each view widened to its share of a 16:9 window. Ghost Race runs a full timed session through to the results and the Best
Ghosts table, and the translucent respawning car renders. Playing as a pak player (not JUST PLAY), a Ghost
Race session writes the pak, and after a restart the profile still remembers the last mode picked. The ghost
car itself shows too: finish all three laps inside the time limit, start another Ghost Race on the same track
with GHOST 1 picked, and the ghost starts inside your car and pulls ahead in your lane. Earlier tries missed
it because no run had finished before the timer, and a ghost never survives a restart (see Ghost Race under
Runtime notes). Not yet exercised: multiplayer with real second pads.

Testing tip: the cheat menu works and unlocks everything without playing through Circuit. On the main menu, highlight
OPTIONS and press L+R+Z+C-Up+C-Right together (keyboard: E+R+Q+T+H) until CHEATS appears; open it with A
(Space; Enter is Start, which always starts the game). Highlight ALL TRACKS, hold L+R and press Z with C-Up+C-Right,
C-Down+C-Left, C-Left+C-Up, C-Down+C-Right in turn (C buttons first, then Z), then press right to switch it ON.

## Enhancements and the original game

Every change to how the game looks or plays is an option, and each option's Original value runs the game as it
shipped. They are in the recomp's settings menu (not the game's own menus), on the General, Graphics and Sound tabs, and are saved as JSON in the config folder
(`%LOCALAPPDATA%\Rush2049Recompiled\`, `~/.config/Rush2049Recompiled/` on Linux, or the working directory when it holds a `portable.txt`), so they can also
be edited by hand while the game is closed. For the original game, set every Original value below.

| Enhancement | Option | Key | Default | Original |

topic (Graphics, Sound, General, Controls), beside RT64's own options, rather than on a tab of its own.

## Replacement music

The game's music is MusyX sequences played through samples of about 5–11 kHz, so it sounds muffled however it is
mixed. You can play your own recordings of the songs instead. None ship with the game: bring your own.

- **Where:** a `music` folder next to `Rush2049Recompiled.exe`, or in the app data folder (the folder holding
  `sound.json`).
- **Names:** the song's two-digit number or its name, then anything: `06.ogg`, `title.flac`, `03 - Trancey.mp3`.
  Case doesn't matter. A song with no file keeps the game's own music.

  ```
  00 bassy      03 trancey     06 title      09 flier
  01 garage     04 seventies   07 retro      10 battle1
  02 night      05 credits     08 stunted    11 battle2
  ```
  The menu plays 06. A race plays its track's song, or the one picked under AUDIO → MUSIC TRACK.
- **Formats:** OGG Vorbis, FLAC, MP3 and WAV, any sample rate, mono or stereo.
- **Looping:** the whole file loops. An OGG with `LOOPSTART` and `LOOPEND` or `LOOPLENGTH` comments (in samples,
  the convention most game rips use) plays from the start once, then loops between those points.
- **Settings:** Sound tab → "Replacement Music" (On/Off, takes effect from the next song) and "Replacement Music
  Volume" (100% by default, up to 200%). The game's own MUSIC VOLUME, pause and fade-outs still apply.

### Where better recordings come from

Barry Leitch scored both the N64 and Dreamcast ports, and the Dreamcast port (also the one in *Midway Arcade
Treasures 3* for GameCube, PS2 and Xbox) has a soundtrack that is mostly the arcade one (Mike Henry), but several
of its songs are other versions of the N64 ones. A rip from a disc you own fills these slots:

```
N64 song      Dreamcast / MAT3 song
00 bassy      Bassy (Downtown battle)
01 garage     Garage (Mission)
02 night      Night (Metro), may differ, see below
03 trancey    Trancey (Warehouse stunt)
06 title      Internet (web browser screen)
08 stunted    Stunted (The Rim stunt)
09 flier      Flier (Disco stunt)
```

They are arrangements of the same compositions, not the same mix, so expect differences in length and
instrumentation. Accounts disagree on Night: one says the Dreamcast Night is the arcade's track 5 and the N64 one
is closer to the Dreamcast's Wingey, so try both. Seventies, Credits, Retro and the two battle clips exist only
on the N64; nothing better than the game's own samples is known for them.

Any other song works too: dropping the Dreamcast's Morning in as `00.ogg` plays it on Marina. No official
soundtrack album of Rush 2049 is known; Barry Leitch's Bandcamp has none.

## Mods

The game loads N64Recomp mods (`.nrm`) from the `mods` folder in its data folder: `rush2049/mods/` when run from
`rush2049/` with `portable.txt` (the dev setup), `%LOCALAPPDATA%\Rush2049Recompiled\mods\` otherwise. They are
enabled when found, and the launcher's mod menu turns them on and off. The mod game id is `rush2049`.

**What a mod can do:**

- **Hook any game function** with `RECOMP_HOOK("name")` (runs on entry, with the same arguments) or
  `RECOMP_HOOK_RETURN("name")` (runs just before it returns). This works in all of the game's code: boot, the
  main code and both overlays. Names come from `syms/rush2049/rush2049.us.syms.toml`.
- **Call game functions and read or write game variables** by name: functions from the same file, variables
  from `syms/rush2049/rush2049.us.datasyms.toml` (`extern s32 current_song;`). Anything without a name can be
  reached by its address.
- **Use what the game exports** (import from `"*"`, declared in `mod_template/include/rush2049_api.h`):
  `recomp_printf` (prints to the console), `recomp_get_window_resolution`, `recomp_get_target_aspect_ratio`,
  `rush2049_get_game_frame_rate`, the runtime's `recomp_alloc`/`recomp_free`, its config and hook APIs
  (mod options in `mod.toml`, `recomp_get_config_*`), and recompui's UI API for menus.
- `RECOMP_PATCH` replaces a game function outright, but with no decompilation of this game that means writing the
  whole function in C, so hooks are the practical tool.

**Names are the API.** `syms/rush2049/names.toml` names the functions we have worked out (`draw_tex_rect`,
`hud_draw_race_timer`, `music_thread_main`, the scheduler's `sched_on_retrace`, …), and gen_syms.py applies
them to the symbol file. Everything else is `func_<address>` (overlays: `ovl1_func_`/`ovl2_func_`). Mods are
built against these names, so names may be added but never renamed or removed. The same goes for the
variables in the datasyms file. A built `.nrm` stores where each hook goes, not its name, so a later rename
breaks a mod's source and leaves its `.nrm` working.

**Writing one:** `rush2049/mod_template/` is a working mod to copy. It hooks `boot_main` and
`hud_draw_race_timer` and prints to the console:

```sh
source tools/env.sh                                  # MIPS_CC, MIPS_LD (Windows: MSYS2's clang, see 03-local-env.md)
ninja -C rush2049/build RecompModTool             # the runtime's pinned N64Recomp, so the mod format matches
make -C rush2049/mod_template CC="$MIPS_CC" LD="$MIPS_LD"
cd rush2049/mod_template && ../build/RecompModTool mod.toml build   # writes build/rush2049_hello_mod.nrm
```

CI's Linux job builds the example mod on every PR and keeps `rush2049_hello_mod.nrm` as a run artifact. `mod.toml`'s `minimum_recomp_version` is checked against the app
version (`version_string` in `src/main.cpp`, now `0.0.1`).

**How it works.**

- The runtime hooks a function by recompiling it again from ROM, with the hook calls added. Rush 2049's main
  code and overlays are only in ROM as deflate streams, so the game entry's `decompression_routine`
  (`build_recomp_rom` in `src/code_loading.cpp`) rebuilds the recomp ROM that `tools/rush2049/extract.py`
  writes: the three segments inflated at their fake ROM addresses. Without it, a hook on anything outside
  boot read past the end of the ROM and crashed at the first call.
- The **patches library** (`rush2049/patches/`) is MIPS C that `patches/Makefile` compiles with clang and
  N64Recomp recompiles (`rush2049/patches.toml`) into `RecompiledPatches/`, linked as `PatchesLib`. Its
  `RECOMP_EXPORT` functions and `RECOMP_DECLARE_EVENT` events are what mods find under `"*"`. Today it holds
  `recomp_printf`, which hands its `va_list` to the native `recomp_vprintf` (`src/mod_exports.cpp`; natives are
  listed in `patches/syms.ld`). It shares `modding.h` and `types.h` with the mod template. The game's own
  enhancements stay C++ hooks in `us.toml`, and nothing has moved into the patches library.
- CMake builds it with `PATCHES_C_COMPILER` and `PATCHES_LD` (default `clang`/`ld.lld`; on Windows pass
  `$MIPS_CC` and `$MIPS_LD`, see "Building and running") and the runtime's own N64Recomp (target
  `N64RecompCLI`). CI's Windows job has no MIPS clang and configures with `-DRUSH2049_PATCHES=OFF`; the Linux
  job builds the library.

## Building and running

Needs the toolchain from [../03-local-env.md](../03-local-env.md) (`tools/env.sh` puts clang-cl, CMake, Ninja,
N64Recomp and RSPRecomp in reach) and a Python venv at `.venv` with `spimdisasm`, `rabbitizer` and `numpy`.
From the repo root, in MSYS2 bash:

```sh
git submodule update --init --recursive
bash tools/rush2049/apply_runtime_patches.sh            # runtime submodule fixes, see "Runtime notes"
git clone https://github.com/shygoo/n64sym ref/n64sym    # signature list for gen_syms.py (MIT); ref/ is ignored
.venv/Scripts/python -I tools/rush2049/extract.py "<path to Rush 2049 (U) [!].z64>"
                                                         # writes roms/rush2049.us.z64 and roms/rush2049.us.recomp.z64
source tools/env.sh
cmake -S rush2049 -B rush2049/build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
      -DCMAKE_C_COMPILER=clang-cl -DCMAKE_CXX_COMPILER=clang-cl \
      -DPATCHES_C_COMPILER="$MIPS_CC" -DPATCHES_LD="$MIPS_LD"   # patches library, see "Mods"
bash tools/rush2049/iterate.sh 30                        # symbols, N64Recomp, RSPRecomp, build, 30 s boot test
```

`iterate.sh` regenerates `syms/rush2049/rush2049.us.syms.toml`, reruns N64Recomp into `rush2049/RecompiledFuncs/`,
generates `rush2049/rsp/musyx.cpp` once, builds, and boots the game for the given number of seconds with its log in
`rush2049/run.log`; `--no-recomp` as the second argument skips the first two steps. Afterwards
`ninja -C rush2049/build Rush2049Recompiled` is enough for source changes. Run `rush2049/build/Rush2049Recompiled.exe`
from `rush2049/`. Saves go to `rush2049/saves/`.

**Finding the ROM.** Until a ROM is stored, the launcher looks for one each time it opens (`src/rom_finder.cpp`):
in the working directory, `roms/` and `../roms/` under it, the exe's folder and its `roms/`, and Downloads, Desktop
and Documents plus one level of subfolders. It considers `.z64`, `.n64` and `.v64` files of 1–64 MiB whose header
names "Rush 2049" in any byte order, and stores the first that passes the runtime's hash check, so the launcher
opens on Start Game. With none found it stays on Load ROM, where picking a file shows the runtime's error dialogs
(wrong game, wrong version, not a ROM); nothing crashes either way. `[rom]` lines in the log say what it found.

**Linux** (Ubuntu 24.04, what CI's `build-linux` job checks; nobody has run the game on Linux yet): install
`clang lld libsdl2-dev libgtk-3-dev libfreetype-dev`, CMake 3.31 and Ninja, then configure with
`-DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++` instead of clang-cl. N64Recomp and RSPRecomp build there
too, and the Python steps are the same with `.venv/bin/python`. The config folder is `~/.config/Rush2049Recompiled/`
(or `$APP_FOLDER_PATH`, or the working directory with a `portable.txt`). A crash prints a backtrace to stderr.

## Triage (`py -3 -I tools/rom_triage.py <rom>`)

- **Graphics ucode: `RSP Gfx ucode F3DEX.NoN fifo 2.08 Yoshitaka Yasumoto 1999 Nintendo.`** This
  is F3DEX2 2.08 NoN `.fifo`, which is in RT64's supported table (see
  [../01-toolchain.md](../01-toolchain.md#3-rt64)). The biggest blocker class is cleared.
- **The triage's "no compression" was wrong.** No Yaz0/Yay0/MIO0/gzip magics, but the main code and both
  overlays are **raw deflate** streams (zlib `wbits=-15`, no header), which have no magic to find. Only the
  boot segment is plain.
- **Audio is MusyX v1** (Factor 5), not libultra's audio library: the RSP string `N64 RSP mixer V1.1` sits in
  boot data at `0x8002D890`. The triage tool only looks for libultra audio strings.

## Memory map

| Segment | ROM (original) | Recomp ROM | VRAM | Text size | Notes |
|---|---|---|---|---|---|
| boot | `0x1000` (plain) | `0x1000` | `0x80000400` | `0x80027DD0` end | Game boot code, libultra 2.0J, MusyX CPU side. |
| boot ucode text | | | `0x80027DD0`–`0x8002C5E0` | | rspboot, F3DEX2, MusyX mixer text linked into `.text`. **Not CPU code.** |
| boot_tail | | `0x2D1E0` | `0x8002C5E0` | `0x1C` | One CPU function after the ucode text: a `cache 0x0D` loop. Stubbed. |
| main | `0xB0CB10` (deflate) | `0x01000000` | `0x80086A50` | `0x89330` (to `0x8010FD80`) | Inflated at boot. Data follows to `0x801249F0`, bss to `0x8017A640`. |
| ovl1 | `0xB5C534` (deflate) | `0x010A0000` | `0x8038A400` | `0x25580` (to `0x803AF980`) | |
| ovl2 | `0xB6FEC4` (deflate) | `0x010D0000` | `0x8038A400` | `0x9740` (to `0x80393B40`) | Shares VRAM with ovl1; probably the battle overlay. |

- **Boot.** The entry clears bss at `0x8002E8E0` (size `0x58170`), sets `sp = 0x80086A50` and jumps to
  `0x800020F0`.
- **Inflate.** `func_80006814(rom, dst, flag)` inflates a raw deflate stream from cart ROM to `dst` and returns
  the size. The main thread calls it at `0x80002334` with `(0xB0CB10, 0x80086A50, 0)`; the wrapper
  `func_800026C0` calls it at `0x800026F4` for everything else. After inflating it runs `osInvalICache` over
  the output, which is where the runtime registers the code (`rush2049/src/code_loading.cpp`).
- **Overlays.** A table of their ROM addresses is at `0x8002B020` (`{0xB5C534, 0xB6FEC4}`). `func_800A11E4`
  loads them: table[0] from `0x800A1384` and `0x800C9040`, table[1] from `0x800A128C`. Both go to
  `0x8038A400`.
- `tools/rush2049/extract.py` writes `roms/rush2049.us.recomp.z64`: the original ROM padded to 16 MiB with the
  three inflated segments appended at the "Recomp ROM" addresses. N64Recomp reads code from there; the
  runtime loads the original ROM.

### Where the boot CPU text ends

libultra links the RSP microcode text into `.text`, after the CPU code. Decoded as MIPS, ucode looks like code
with `jal 0x84000xxx` targets and dense COP2 (`lwc2`/`swc2`/vector) ops. That mattered: a `jal 0x80001088` in
the ucode text split `func_80000FE8` in the middle and broke the first recompile. The first IMEM-range
`j`/`jal` in boot is at `0x80027DD0` (rspboot), and nothing in the CPU code calls past it except
`0x8002C5E0`.

## Function naming

`tools/rush2049/gen_syms.py` writes `syms/rush2049/rush2049.us.syms.toml`:

1. **Boundaries** from spimdisasm (`--function-info`), with false splits merged (a function that branches into
   the next one, which nothing calls).
2. **libultra names** from n64sym's signature list (MIT, `ref/n64sym`): CRC32 of the first 8 bytes and of the
   whole function, relocated fields masked. Matches that collide under several names are dropped, as are a
   few names that hit game code (`UNTRUSTED_NAMES`).
3. **Hand names** (`MANUAL_NAMES`) for what signatures can't see: `exceptasm.s` (`__osExceptionPreamble`,
   `__osException`, `send_mesg`, `handle_CpU`), the PI/SI access-queue pairs (identical code, different
   globals), and functions identified by their calls and registers (`viMgrMain`, `osEPiStartDma`,
   `osAiSetFrequency`, `osContInit`, …).
4. Our own names from `syms/rush2049/names.toml` (`[[func]]` with `section`, `vram`, `name`). Mods hook by
   these names, so add to it freely but never rename or remove an entry (see "Mods"). `us.toml` hooks use them
   too.

Names matter to N64Recomp beyond readability: it drops or reimplements libultra functions **by name**, so an
unnamed libultra function that touches hardware gets recompiled and crashes, and a game function wrongly given
a libultra name silently disappears. `func_8000262C` (the game's lock release, `osSendMesg` on its own queue)
matched `__osSiRelAccess`'s signature from a debug libultra build and was being dropped that way.

`tools/rush2049/xmatch.py <other rom> <other syms>` compares unnamed boot functions with another game's
named ones by address-masked code. Against Rush 2 (`ref/rush2recompiled`'s symbol file, used as facts only)
it confirms the scheduler, `sprintf`, the inflate routines and a few libultra helpers.

## What N64Recomp can't translate

- **Speech decoder asm island, `0x800277D0`–`0x80027DD0`.** Hand-written GSM 06.10 full-rate decoding
  stages. The code reads the PC with `bltzal $zero`, calls local subroutines with `bal`, jumps through
  `jalr $t3` to per-section LAR interpolation stubs and keeps its tables inline (QLB `0CCD 2CCD 5333 7FFF`,
  the small-xmaxc table at `0x800278BC`). Entry points, all called from `func_800265xx`:
  - `0x800277D0`: APCM inverse quantization and RPE grid positioning (xmaxc, Mc, xMc[13], erp[40]).
  - `0x800278C4`: long-term synthesis (state, Ncr, bcr, erp). The lag is kept at state `+0x166` and only
    replaced when 40..120.
  - `0x80027B44`: short-term synthesis lattice and de-emphasis (0x6E14) over a 160-sample frame, with the
    LARpp sets at `+0x168`/`+0x178` picked by the halfword at `+0x188`, v[0..7] at `+0x140` and msr at
    `+0x164`. Output is clamped and masked with `0xFFF8`.

  They are `ignored` in `us.toml` and implemented in `src/gsm_decoder.cpp`, translated from the assembly
  rather than from the specification, so they keep its 32-bit arithmetic.

  **The decoder is dead code in this ROM.** Every path into it starts at a function nothing references, by
  `jal`, by a `lui`/`addiu` pair or as a pointer in ROM data: `800277D0` ← `80026360` ← `80026558` ←
  `80026640` (unreferenced) or `800268D0` ← `80025F74` ← `8002574C`, a stream callback that only
  `80025C68` (unreferenced) installs at `0x80038024`. The other entry points in `0x80025594`–`0x80026640` are
  unreferenced too. It is a linked-in streaming and speech library the game never uses. The translation stays
  so the island doesn't need a stub, and it logs `[gsm] first speech frame` if a path turns up after all.
- **`0x8002C5E0`**: `cache 0x0D` (create dirty exclusive) over a buffer. Meaningless on PC; stubbed.

## Runtime notes

- **Threads.** The game stops and restarts thread 5 (`func_800E7808`, struct `0x80034840`) from other threads.
  Upstream `osStopThread`/`osStartThread` on another thread corrupted the run queue, so
  `runtime-patches/N64ModernRuntime-0001-threads-and-ai-events.patch` fixes `thread_queue_remove` and makes
  a restarted thread go back into the message queue it was blocked on. `tools/rush2049/apply_runtime_patches.sh`
  applies the patches to the submodule (it skips ones already applied).
- **Busy-wait loops.** ultramodern runs one game thread at a time and only delivers VI/SP/DP/AI messages inside
  OS calls, so a loop polling memory another thread or an interrupt changes never ends. Every such loop gets a
  `yield_self_1ms` hook. `tools/rush2049/find_spins.py` lists the polling loops and `--toml` emits the hooks;
  the generated block sits between the markers in `us.toml`, and the audio thread's spin at `0x8008AB44` has
  its own hook.
- **Audio pacing.** The AI DMA thread (`func_80010A40`) waits for one `OS_EVENT_AI` per 0x300-byte buffer
  (192 stereo frames at 22050 Hz, about 115 per second). Upstream sends one per VI, which played audio at
  half speed; the runtime patch sends one per buffer's worth of audio played instead.
  That clock and the device's drift apart, and the game queues buffers in bursts, so SDL's queue swings by tens
  of ms. The old output (upstream's) dropped every 2nd sample of a buffer once the queue passed 100 ms by a count
  that divided device bytes by the game's rate, 46 ms of real audio: in 150 s of the attract demo that hit 62
  buffers, and with the queue held that low 475 buffers found it empty (a few ms from running dry).
  `queue_samples` now nudges the resampler's speed instead, up to 1% either way, to hold the queue near 40 ms:
  no skips, and once settled 5 empty readings in the next 100 s. `--probes` prints the queue's mean and max.
- **MusyX.** Audio tasks run through mupen64plus-rsp-hle's MusyX v1 HLE by default (`src/hle/`, vendored,
  GPL-2.0-or-later). `--musyx lle` runs the game's microcode through RSPRecomp instead (`rsp/musyx.cpp`,
  generated, not committed), and `--musyx compare` runs both on the same input every 25th task. They agree.
  The sample-address callback `func_8010FD60` turns addresses into cart KSEG1 addresses
  (`0xB0000000 | addr`), so the mixer DMAs samples straight from ROM.
- **High-quality mix.** The HLE also renders every subframe at twice the game's rate (44.1 kHz), and
  `queue_samples` plays that in place of the game's buffer. It is a side mix: RDRAM and the game's own output are
  exactly what the original mix writes (`musyx_hires_t` in `src/hle/musyx.c`). Voices are interpolated with a 16-tap
  Kaiser-windowed sinc instead of the N64's table: flat to 0.4 of a sample's rate (the table is -6.5 dB there),
  -1.2 dB at 0.45, and images from 0.6 on are 53 dB down. The game loads only the 3 samples past each read position
  the table needs, so the side mix reads one more ADPCM frame (or 32 PCM16 samples) before and after each load,
  from the same stream (`hires_load_voice`). The game streams samples through 0x600-byte blocks in RDRAM, and a
  load's second pointer names the next block before the voice gets there, so a read past a block's end continues
  in that block; before the start of a block the first sample is held. In 40 s from boot, 97% of the windows that
  reach past a load matched what the game decoded a subframe later, and the rest were at one loop point, where the
  data after the loop end differs from the loop start by at most 80 in 32768. About a fifth of the voices play above 1x (12% at exactly 2x, an octave up, on the title screen), and the original mix
  aliases those; at twice the rate they keep their treble up to 22 kHz. Above 2x one output step skips samples, so
  the kernel is stretched by the step (to 64 taps at 4x, as far as the extra samples reach) and cuts at the output's
  Nyquist frequency instead of the voice's: what folded back below 17.6 kHz at full level is 53 dB down or more
  (`tests/musyx_hires_test.c`), and at or below 2x the output is bit for bit what it was.
  No voice plays above 2x in 200 s of boot, menus and the attract race (`--dump-audio` captures of the first 40 s
  match sample for sample), so this is for faster voices elsewhere and for mods. Voices at or below 1x, the delay effect and
  the delayed cc0 surround channel go through a 97-tap low-pass just under 11 kHz, because above that they hold only
  interpolation images. The cc0 surround channel is silent in this game, though: MusyX folds it into stereo out of
  phase (+cc0 left, -cc0 right, Dolby Surround style), but only its surround output mode fills it, and the game's
  sound options offer just STEREO and MONO. A probe on cc0 read exactly 0 every second for 150 s of boot, menus and
  the attract-mode race, so a headphone-friendly fold of it would change nothing. Each output buffer is matched to its high-quality copy by address and contents, and
  anything unmatched (the silence before the first audio task) is upsampled from the game's. `--musyx native`
  and the Sound tab's MusyX Mixing set to Original play the original mix; `--probes` counts matched and unmatched
  frames. The copy is float and not clamped to 16 bits, so the peaks the original mix clips come through: the
  output halves them before the device. In the first 100 s after boot 0.1-1% of samples go past 16-bit full
  scale (the game's mix clips them), with peaks at about twice full scale, so a few still reach 1.0 after halving.
- **The MusyX delay effect is never used.** Its only constructor (`func_80010E80`, the one writer of the effect
  pointer at `0x800382E8` besides the destructor) is reached only from `func_80014BD8` and `func_80020528`, and
  nothing calls or references `func_80020528`. Every voice's send to the effect (the fourth envelope) is 0, and
  boot, attract, menus and a race never pass an effect to the microcode. The high-quality mix still runs it, in
  float at 44.1 kHz on its own copy of the game's circular buffer, kept in step by a 16-bit shadow of what the game
  wrote (`sfx_hires_stage`), for a mod that turns it on. Driven offline with game audio and made-up settings it
  matches the original to 37 dB while the echo is loud. The original's tail turns to rounding noise around -82 dBFS
  and cuts to silence 1.5-3 s after the input stops; the float tail decays on smoothly.
- **Output resampling** (`src/audio_resampler.cpp`). The mix reaches the device rate (48 kHz) through a 64-tap
  Kaiser-windowed sinc that keeps its input from one 4 ms buffer to the next. SDL 2 can't do this: `SDL_ConvertAudio`
  has no state and pads every buffer with silence, which left distortion 36-42 dB under a 5-10 kHz tone (the 4 frames
  the old code overlapped hid the start of each buffer, not its end), and `SDL_AudioStream` drops the fraction
  of a frame each put leaves over, about 0.8 frames per buffer here (-20 to -40 dB, and 0.05% sharp). The resampler
  is under -105 dB from 1 to 15 kHz, passes to about 18 kHz, and lags 32 input frames.
- **Audio levels.** The mix wanders a lot: the per-second mean goes up to ±7000 and RMS reaches ~11000
  once the music builds. Project64 2.3 (LLE RSP, recorded through WASAPI loopback) shows the same thing, so it
  is the soundtrack and not a bug. The game's own mix clips too: both recordings have the same RMS (0.238)
  and about the same share of samples above 0.97 of full scale once resampled to 44.1 kHz (0.21% recomp,
  0.25% Project64). Project64's never go above 0.99, so its output path limits the peaks (likely the Windows
  shared-mode limiter), while the `--dump-audio` file holds the game's raw samples. Playback scales them by
  0.5 before the device, so the recomp doesn't clip on output, and the high-quality mix, which isn't clamped,
  doesn't clip at all.
- **Limiters** (`src/audio_limiter.cpp`). Two stereo-linked look-ahead limiters (3 ms look-ahead, ~60 ms release)
  keep the output under full scale. The first, on the game's own mix after the halving, bends peaks above 0.9 toward
  1.0. The replacement music is added after it, and a mastered track sits near 0 dBFS all the time, so a loud hit
  over a loud bar still summed past 1.0. The second limiter runs on that sum and bends peaks above 0.95 toward 0.99,
  so the music on its own is left alone. In 155 s of game audio with a loud mastered track at 100%, the sum went past
  1.0 on 55 samples, and after the limiter on none. It engaged 18 times, by 1.2 dB at most. At 200% replacement
  volume it was 493 samples, then none, with 11% of frames limited by up to 3 dB. Without music it engages a few
  times, by under 0.1 dB. `--probes` prints both as `limiter` and `music limiter`.
- **Music replacement** (`src/music.cpp`). Music is driven by commands to the music thread `func_800992AC` through
  the queue at `0x801427A8`: type 0 plays the song at +4 (0–11), 1 stops, 10 sets volume (float 0–1 at +4, fade
  seconds at +8, music when the byte at +C is set, sound effects when +D is), 2–6 are sound effects. `0x80110240`
  holds the playing song, −1 for none. A hook at `0x80099390`, where the thread switches on the type, sees every
  command. When a file exists for a song its play command's type becomes 0xFF, which the thread ignores, so the
  sequence never starts; the file is decoded with the vendored stb_vorbis and dr_libs (`lib/decoders/`), resampled
  with an `SDL_AudioStream` and mixed in `queue_samples()` at the device rate. Findings that set its behaviour:
  - MUSIC VOLUME (0–10, byte `0x80146114`) reaches the thread as a type 10 target of setting/10. Measured on the
    title song, setting 5 plays the game's music 12.8 dB below setting 10, so the volume is squared, and the
    replacement squares it too.
  - The game's music plays at about −16.6 dBFS RMS (AC) on the title screen with peaks near 0.55, after the 0.5
    above. The replacement is halved the same way, so a normally mastered recording (about −12 dBFS RMS) at 100%
    comes out near the original's level with the same headroom for sound effects.
  - Leaving the menu for a race sends a fade to 0 over 3 s and then, 6 ms later, a stop. The stop ends the
    sequence at once (`func_80096238`), but its notes ring out. A recording stopped there would cut mid-note, so a
    stop lets a running fade-out finish, or gives a 0.25 s release, and the file stops once silent.
  - Pause sends volume 0 over 0.05 s, and unpausing sends volume 1 over 1 s, so pause needs nothing of its own.
- **Controller Pak.** The game saves only to the Controller Pak (no EEPROM, SRAM or flash calls).
  `src/controller_pak.cpp` implements `osPfs*` over a `.mpk` image per port
  (`saves/controllerpak_<n>.mpk` under the config folder, the layout emulators use), and its definitions take
  the place of librecomp's no-pak stubs at link time. Every 30 frames the game queries the controllers
  (`func_800E73D8`), `func_800A43FC` turns status bit 0 into a "pak inserted" flag (per-port struct at
  `0x80144030`, stride `0x304`: `+1` handled, `+2` inserted, `+3` removed), and `func_800A377C` calls
  `osPfsInitPak`, then `osMotorInit` only if that fails. It compares each pak's 32-byte ID block across ports
  to spot a pak moved between controllers, so `osPfsInitPak` copies the image's ID block into `OSPfs.id`, and
  each port's pak is formatted with its own serial. All four ports always report a controller with a pak in it, so
  every pak can be loaded from and saved to whoever is playing. A port nobody plays on reads as a pad left alone
  (no buttons, stick centred), so in single-player mode ports 2-4 don't echo port 1's input, and the game offers
  up to four players whatever is plugged in.
- **Large Controller Pak.** libultra addresses a pak of up to 62 banks of 32 KiB (`PFS_MAX_BANKS`): bank 0 holds
  the ID area, one inode table per bank, their backups and the note table, and its data starts at page `2B+3`;
  every other bank's data starts at page 1, and an inode entry names a page as `bank << 8 | page`. Nintendo only
  made one-bank paks. "Controller Pak Size" (General tab) picks one bank or 62. 62 is 7748 data pages; a profile
  takes 9, and the note table still has 16 entries, so the game never runs out of pages. The image file follows
  the size (2,031,616 bytes at 62 banks). When the game initializes a pak of the other size, `osPfsInitPak` moves
  its files, note slots and contents unchanged, onto a newly formatted pak of the size picked and writes it out
  (`[pak] port 1: 1 bank(s) -> 62` in the log). A pak whose files don't fit in one bank stays large.
- **Ghost Race** (game mode word `0x8014A110` == 2). A ghost is a replay of the player's *inputs*, not of
  positions: `func_800E5D64` records 3 bytes per 60 Hz tick for the whole race, into the object at
  `*(0x80142500)` (`+0x50` sample count, `+0x54` capacity, `+0x05` mode: -1 recording, 0 closed, 1 playback).
  Capacity is `(limit + 10) × 60` from the per-track time-limit table at `0x80111754` (225, 285, 300, 390, 330,
  450 s), so the whole time limit always fits. The ghost exists only if you finish all the laps; when the timer runs
  out, the recording is dropped (`func_800D510C`). After a finished race, `func_800F64D4` keeps it in the in-RAM
  ghost table (`func_800CC040` with `a3=1`, which never writes the pak). The *next* Ghost Race on that track
  offers it as GHOST 1 on the car screen, and `func_800F6AB8` adds it as car 1 (car array `0x8014A250`, stride
  `0x808`, position at `+0x794`; car count halfword `0x8014A108`). Every car starts on grid slot 0, so the ghost
  starts inside your car and only separates once it drives off. Car-to-car collision is off in this mode
  (`func_800CED3C`), and the body is drawn with alpha `0x80` (`func_80093B20`). A car that sits still for about
  10 s is respawned. A ghost never appears in the race it is being recorded in, and none survive a restart:
  the SAVE GHOST prompt that writes one to the pak only appears when byte `0x801148E4` is set, and its only writer
  (`func_800CCEFC`, `0x800CD018`) sets it when the loaded pak profile's name is exactly `000F1CC5 EJK`
  (`0x801211CC`). That looks like a developer code, so retail ghosts last only for the session.
  To test without driving a 47-second lap: write a bigger float into the track's entry in `0x80111754` before
  the race starts (the HUD countdown follows it), finish the race at any pace, then pick NEW TRACK, same track.
- **Keyboard defaults.** The game's own CONTROLS screen: gas A, brake B, steer with the stick, shift up R, shift
  down C-Down, reverse C-Left, abort C-Up, view L. The frontend's stock keyboard defaults put the C buttons on the
  arrows, so Up aborted and Left reversed. `src/config.cpp` overrides them: the arrows are a second stick (steering
  and menus, like WASD), and the C buttons are T (up), F (left), G (down) and H (right). The rest are unchanged:
  Space A (gas), Left Shift B (brake), E L, R R, Q Z, Enter Start, I/J/K/L the D-pad.
- **Gamepad defaults.** Any pad SDL knows as a game controller works: Xbox 360 and later Xbox pads through XInput,
  PlayStation and Switch Pro pads through SDL's own drivers, and the N64 and GameCube pads and adapters in
  `recompcontrollerdb.txt`. The frontend's stock layout is an N64 one, with gas and brake on the A and X face
  buttons and the triggers on R (shift up) and Z, so `src/config.cpp` sets driving defaults for a modern pad
  (Xbox names; other pads have the same buttons in the same places):

  ```
  RT, A                   gas (A)
  LT, X                   brake (B)
  RB                      shift up (R)
  LB, right stick down    shift down (C-Down)
  right stick left        reverse (C-Left)
  right stick up, R3      abort (C-Up)
  right stick right       C-Right
  Y                       view (L)
  B                       Z
  left stick              steer
  D-pad, Start            D-pad, Start
  Back                    the recomp's menu
  ```

  Like the keyboard ones these are only defaults: a pad that already has a saved profile keeps its bindings until
  "Reset to defaults" on the Controls tab, and the game's own CONTROLS screen still applies.
- **Rumble Pak.** One accessory slot per controller, so the General tab has a "Controller Accessory" option
  (Controller Pak by default, or Rumble Pak). With Rumble Pak, `osPfsInitPak` fails with `PFS_ERR_DEVICE` (11),
  as libultra's ID check does on a Rumble Pak. `func_800A1E94` maps 10 and 11 to "not a Controller Pak", and then
  the game calls `osMotorInit`. It only trusts the result if `OSPfs.queue` was filled in, which libultra does
  before the ID check, so the failing path writes `queue` and `channel` too. Without that, the game reads the port
  as having no pak at all. Verified: the Player 1 screen shows RUMBLE PAK, the game starts the motor in a race
  (`[rumble] first motor start` in the log), and the `.mpk` is left untouched.
- **Frame rate.** The original draws at 30 fps: the scheduler swaps a finished frame only when the retrace count
  has moved by at least 2 since the last swap. That check (`sltiu $at, $t3, 2`) happens in two places, when the RDP
  finishes (`func_80000C54`, 0x80000CFC) and on retrace for a pending swap (`func_80000880`, 0x800008C8), and the
  next frame starts only after a swap. That is the whole cap. Game logic uses measured time (the RDP-done path keeps
  an `osGetTime` delta at 0x80124F70), so speed doesn't depend on frame rate. Measured at 60 fps, the race clock
  advanced 21.73 s over 21.77 s of wall time. The Graphics tab's "Game Frame Rate" option (60 FPS by default, or
  30 FPS Original) feeds `rush2049_frame_pace`, a hook before both checks that turns a delta of 1 into 2. The same
  count gates the next graphics task while a swap is pending (`func_80000BA4`, 0x80000C14, `$t2`), paced the same
  way. Probes: about 300 RDP completions per 300 retraces at 60, and 150 at Original.
  The third setting, Match Framerate, goes above 60 with a faster VI: one game frame for every frame RT64 presents,
  so it follows the Framerate option (Display is the monitor's refresh rate, Manual its value, Original 60; never
  below 60). The log says `[frame rate] <fps> fps, VI <hz> Hz (display <hz> Hz)` on each change.
  `runtime-patches/N64ModernRuntime-0002-vi-rate.patch` adds `ultramodern::set_vi_rate`. Its VI thread paces AI
  events by the audio played over every VI that passed, and on Windows it sleeps on a high-resolution waitable
  timer: `Sleep` rounds up to the system timer period, which at 120 Hz dropped the VI to 48–80 a second. Linux
  keeps ultramodern's own `std::this_thread::sleep_until` (clock_nanosleep), which already wakes within microseconds.
  The scheduler's retrace handler forwards every retrace to its clients (the main, controller, audio and music
  threads), and the music sequencer counts them. Above 60 a hook before that loop (0x8000090C,
  `rush2049_retrace_clients`) sends them itself: the main thread (queue 0x8002ECF8) gets every retrace, because it
  starts a frame only on one, and the others get 60 a second. RT64 works out the game's rate from how often the
  framebuffer changes, counting at 60 Hz, so above 60 each frame's list also says the rate with
  `gEXSetRefreshRate`, in the place of its first pipe sync (`src/widescreen.cpp`). Without it, RT64 takes the game
  for 60 fps and interpolates.
  The main thread's retrace handler (`func_800EE5DC`) starts a frame when no swap is pending, its three frame
  flags (0x80035470–72) are clear, the retrace count has moved, and fewer than 2 frames are in flight (0x80114730:
  up when the logic thread's 0xABE message sends the list out, down on message 2). RT64 starts a frame's workload
  only once the previous present is handled, and with vsync a present waits for the display, so the game tops out
  at about twice the display's refresh rate. Measured on a 30 Hz display at a 120 Hz VI: 60 fps with vsync, and
  with vsync turned off in a test build 85–114 fps in the menus and 60–82 in a race. Audio stayed at 116 buffers a
  second and input at 60 reads a second throughout. The race clock (float seconds at 0x801543CC) tracked wall time
  at 30, 60 and 120 Hz: 40.38, 40.37 and 45.37 s over 40.38, 40.37 and 45.39 s.
- **Widescreen and resolution.** RT64 widens the 3D view at runtime (Graphics tab: Aspect Ratio Expand, the
  default) whenever the game's viewport spans the whole framebuffer, which covers single-player races and the
  attract demo. Menus are drawn 4:3; the game fills the bars beside them itself (Widescreen menus, below). Split screen's views are narrower than the screen, so
  RT64 leaves them 4:3 on its own; the game widens them itself (Widescreen split screen, below). Resolution (Original, Original 2x, Auto) and MSAA are RT64's options on the same
  tab, and Auto renders at window resolution.
- **Widescreen HUD** (`src/widescreen.cpp`). The race HUD is texture rectangles at 4:3 positions, all drawn by
  `func_80087110(x0, y0, x1, y1, …)`, which appends `G_TEXRECT` + `G_RDPHALF_1` + `G_RDPHALF_2` at the display list
  pointer in 0x80149438. Hooks at its entry and its single exit (0x800877FC) rewrite that triple in place as RT64's
  `gEXTextureRectangle` (also 24 bytes) with a left origin for rects ending by x 58 (speedometer, gauge) or a right
  origin for rects starting from x 232 (lap, counters, minimap, timer). Centred messages stay put. Inserting a
  `gEXSetRectAlign` before the rect didn't work: callers keep their own copy of the display list pointer across the
  call and overwrite anything added. Two more patches go into each frame's list before the task starts (a hook in
  `func_80000E20` before `osSpTaskLoad`). The list's first command, `gsSPSegment(0, 0)`, is a no-op (segment 0 is
  never anything else), so it becomes `gEXEnable`, which RT64 needs in every list. The HUD's full-screen scissor
  would clip the moved rects to 4:3, and it follows a pipe sync, so the pair becomes a `gEXSetScissor` from the left
  edge to the right edge. All of this applies only in a single-player race (split screen is below). A race is when the timer
  (`func_8010761C`) was drawn in the last 8 retraces (at 60 Hz; more at a faster VI), and split screen is a frame whose top-level list sets a
  viewport narrower than 320. HUD Placement on the Graphics tab sets how far the HUD moves, and Original turns
  all of this off.
  The two spinning coin icons by the counters are 3D models drawn among the world's objects, the only ones whose
  matrix has 10 in its bottom-right corner. When one's origin projects into the right (or left) HUD band, its
  matrix + call + pop triple becomes a call to a list in the recomp heap (read in RT64's extended RDRAM mode) that
  draws it under a viewport anchored to that edge, which RT64 slides as far as the rects. `--dump-dl <file> <seconds>`
  (`src/dl_dump.cpp`) writes a frame's display list as text and was how the HUD was found.
- **Widescreen split screen** (`src/widescreen.cpp`, `runtime-patches/rt64-0001-viewport-edge-origins.patch`). RT64
  only widens a viewport that spans the framebuffer and has no origin; anything else keeps its 4:3 shape. Each
  split-screen view is a top-level `gSPViewport` + pipe sync + `G_SETSCISSOR` (two-player: x 2–242 with the minimap
  panel at 240–320; four-player: quadrants meeting at x 160). The RT64 patch adds `gEXSetViewportAlignEdges`, a
  viewport whose left and right edges follow different origins: each edge moves as an edge of a rect with that
  origin would, the triangles stretch to fill the space between them, and the projection is widened by as much, so
  the picture keeps its aspect ratio. In the same hook as the HUD patches, with Split-Screen Aspect Ratio at Expand,
  each view's three commands become a call (extended RDRAM mode on, `gSPDisplayList`, off) to a list in the recomp
  heap that sets the same viewport with edge origins and the scissor with the same origins. A view edge in the left
  quarter of the screen follows the left edge, one in the right quarter the right edge, and one in between the
  centre, so the two-player views run from the left edge to the panel at the right edge, and the four-player views
  meet in the middle. The HUD follows: in split screen every rect `func_80087110` draws anchors to its view's left
  edge, right edge or centre (left, right or middle third of the view; the centre is the origin halfway between the
  view's two), a rect outside the views anchors to the nearest view edge (the four-player timer sits on the centre
  line), and one across the whole screen stays put. The borders between views and the four-player score boxes are
  `G_FILLRECT`s, each followed by a pipe sync, so each pair becomes RT64's extended fill rect: the borders before
  the first view are copied into a heap list with a scissor across the window, and the score boxes are rewritten
  where they are, in the HUD's list, inside the range `func_80087110` wrote this split-screen session (static lists
  are never touched). A fill across the screen gets a left and a right origin and stretches. The patch also fixes
  RT64 dropping such a fill: it compared the raw right coordinate (relative to the right edge, so negative) with the
  left one before moving them to their origins. The coins are anchored as in single player, by where they sit in
  their own view. The edge origins move by RT64's HUD Placement share, so at HUD Placement Original the views stay
  4:3 too. Menus, including the two-player car select, aren't split screen; they're widened on their own (below).
- **Widescreen menus** (`src/widescreen.cpp`). Every menu screen (main menu, mode, track and car select, the
  two-player screens) sits on one 320×220 picture of a circuit board with a round emblem in the middle, drawn by
  `func_80087110` as texture rectangles: rows 256 pixels wide from the left edge (x 0–255, 8 lines each) and a
  column 64 wide at the right edge (x 256–319, 32 lines each). The menu's buttons and titles are drawn over it at
  fixed 4:3 positions. Compared at 16:9: stretching the whole picture makes the emblem oval, and stretching only the
  outer 64 pixels smears the circuit lines to nearly twice their width; anchoring the B/A buttons to the window's
  edges would take them off the picture. So the menu stays where it is and the picture carries on: with Menu Aspect
  Ratio at Expand, each strip's texture rectangle becomes, in place (24 bytes, like the HUD's), a call to a list in
  the recomp heap that pushes a scissor across the window, draws the strip, draws its mirror image across the screen
  edge (`gEXTextureRectangle` with the step in s negated), and pops the scissor. The 64-wide column is drawn once
  more beyond its mirror, so both bars fill out to 128 pixels each side, about 21:9; wider windows show black past
  that. The title screen's picture is laid out the same way but drawn in copy mode (4 texels a step); it's a
  picture rather than a pattern, so only strips drawn one texel to a pixel (`dsdx` 1.0) are mirrored and the title
  stays pillarboxed. None of this runs in a race or in split screen. It needs `gEXEnable`, so with HUD Placement at
  Original the list's first command is still patched when Menu Aspect Ratio is Expand, and nothing else is.
- **Hi-res font** (`src/hires_font.cpp`). Every font (menus, race HUD, messages) is a 4-bit intensity atlas 96
  texels wide, drawn as texture rectangles, so it is blocky at window resolution. The fonts come from the ROM, so no
  texture pack can ship in the repo: the game makes its own. Before each graphics task starts (the same
  `func_80000E20` hook), the display list is walked with a copy of RT64's load block TMEM emulation (a load tile or
  TLUT isn't emulated and marks TMEM unknown), and each intensity texture a `G_TEXRECT` or `gEXTextureRectangle` draws is hashed with
  `RT64::TMEMHasher` exactly as RT64 hashes it. A new hash is upscaled 4x (Catmull-Rom bicubic, then a contrast
  curve of 2.5 around half the atlas's peak: edges stay clean and the one-texel gaps inside glyphs stay open, which
  a threshold or Scale2x doesn't) and written as an RGBA8 DDS with mips to `hires_font/v1/` in the app folder, with
  an `rt64.json` listing them (shift `none`: `half` pulls slivers of neighbouring glyphs in). That folder is
  registered as a built-in pack below any user packs, through `recompui::renderer::set_builtin_texture_packs`, which
  `runtime-patches/RecompFrontend-0001-builtin-texture-packs.patch` adds. Only the first frame that draws a font
  shows the original; the pack persists across restarts, and bumping `pack_version` throws an old upscale away.
  Hi-res Font on the Graphics tab turns it off. Not affected: the seven-segment speedometer and odometer, which are
  colour textures. The generated pack is ROM-derived and must never be committed (`/rush2049/hires_font/` is
  ignored).
- **Rewind** (`src/rewind.cpp`). Holding Rewind (a game action on the Controls tab, added by
  `runtime-patches/RecompFrontend-0002-rewind-input.patch`) in a single-player race runs the whole race backwards.
  Nothing is kept: cars, clock, laps, checkpoints, wrecks and the ghost being recorded all go back. The race is the
  game's RAM from the end of the main code (`0x8010FD80`) to 8 MB, minus what belongs to something else. A hook in
  the frame loop (thread 7, `func_800FD464` at 0x800FD6A4, after the frame's logic and before it draws) saves it each
  race frame (state word `0x801174B4` == `0x00400000`; menus pass the same point) as a diff against a shadow copy:
  the changed 64-byte pieces with their old contents. Holding Rewind puts back what the last tick changed and applies
  the newest diff. A frame is skipped while thread 5 is inside a tick (hooks around `func_800E7808`'s tick call), and
  when the race clock (float at `0x801543CC`, the tick counter at `0x80143FF4` times a constant) hasn't moved, so a
  pause neither saves nor rewinds. A race frame changes about 40 KB, so the 128 MB cap holds about a minute.
  Split screen (from the HUD's display list walk) and Rewind Off on the General tab clear the history.
  What isn't the race's was found by diffing RAM at every ultramodern thread switch and marking each word with the
  threads that wrote it. Anything another thread also writes must stay live, or that thread spins forever on a list
  half put back: the OS message queues, controller and pak state, the scheduler's and graphics task's state, vertex
  buffers, Z-buffer and framebuffers, the tick's timestamp, and all of the sound side (`music_thread_main`'s
  queues and tables from `0x80142728`, including the pool of 128 sound commands at `0x80142DD8`, the sound
  manager's lists at `0x80143FF8`/`0x80144020`/`0x80144C50`, its sounds up to `0x80218A00`). Nothing the race saves
  points into those. The particles (`0x80155220`, lists at +0x10/+0x14) are only thread 7's and are saved; leaving
  out half of them spun `func_800B066C` the same way.
  Because the sound side stays live, the race knows its sounds only by the ID `func_80092360` returned (sound node
  +0xC). A sound started in the stretch that was rewound is unknown to the race afterwards. One-shots end, and
  loops end when their owner handle (+0x3C) dies, but an ownerless loop (+0x19 set, +0x3C zero: the ambient sounds
  1 and 73, restarted at each unpause) would play on, and the race starts another when it gets there again: each
  rewind across an unpause left about six. When Rewind is let go, every ownerless loop whose ID is nowhere in the
  race's memory gets +0x19 cleared and its +0x20 timer set past -10, so the sound thread frees it at its next
  update (`func_80098FB8`). The race's own IDs are always in its memory as whole words.
- **Expansion Pak.** The game checks for 8 MB and restricts content without it (some path objects and animated
  textures). The runtime reports 8 MB in `osMemSize`.
- **Prior art.** bryantmh/rush2recompiled (Rush 2, no license: facts only, no code) uses the same engine
  recipe: inflated segments at fake ROM addresses, a `load_overlays` hook after inflate, its own
  `osStartThread`/`osStopThread`, file-backed `osPfs*`, and yields inside busy-wait loops on the graphics task
  counter. Its port plan says a separate 2049 recomp would be the better route.
- **Decomp.** cabi24/SFRush2049-decomp targets the same SHA-1 (about 20% matched, no license, IDO 5.3
  `-mips2 -G0`).

## Performance

The game's own code costs next to nothing; the CPU time goes to RT64 turning display lists into GPU work. Measured
with `--profile` in the attract race after `--boot` (an RTX 2070 host, nothing else running), RT64's display list
thread took about a third of a core and its frame matching thread (interpolation) about a quarter, and pinned to a
single core the game fell to 55–57 frames a second. Since:

- **Build flags** (`CMakeLists.txt`). RelWithDebInfo inlines fully (`/Ob2` instead of `/Ob1`), and every target,
  RT64 and the runtime included, is built for Nehalem (SSE4.2, POPCNT), like the recompiled code already was.
- **Texture hashing** (`runtime-patches/rt64-0002-cpu-hot-paths.patch`, `src/common/rt64_tmem_hasher.h`). RT64
  hashes every texture a draw uses, about 1,600 a frame here, mostly CI4. The palette indices a texture uses are
  gathered as a byte per value and turned into a bitset at the end, instead of a bit at a time, and all the bytes
  the hash covers are collected into one buffer and hashed at once rather than streamed row by row and palette
  entry by entry. XXH3 gives the same hash for the same bytes however they are split, so hashes are unchanged:
  checked against the original over 20,000 random tiles for every hash version. Remembering the hash while TMEM
  is untouched doesn't pay: the game loads a texture before nearly every draw, and only 8% of hashes repeat
  without a change to TMEM in between.
- **Frame matching** (same patch, `src/hle/rt64_game_frame.cpp`). The call hash maps and the transform, tile and
  look-at check sets were `std::multimap`s and `std::set`s rebuilt every frame; they are now vectors, sorted once,
  in the same order the containers gave, so matching picks the same pairs.
- **Hi-res font scan** (`src/hires_font.cpp`) copies load blocks a word at a time.

Afterwards the display list thread takes about a fifth of a core and the matching thread about a tenth, and the
game holds 60 frames a second on one core. The GPU side isn't measured yet: RT64 has no GPU timers, and the
defaults (Auto resolution, MSAA 2x, interpolation to the display rate) are the settings to lower on a weak GPU.

## Developer flags

| Flag | Effect |
|---|---|
| `--boot` | Skip the launcher and start the game |
| `--stacks` | Every few seconds, print every game thread's stack and the probes |
| `--probes` | Print the probes only (scheduler messages, audio buffers, audio queue, input reads, pak flags) |
| `--dump-audio <wav>` | Write the game's audio as it reaches the output, before resampling and volume, to a 32-bit float WAV file (the high-quality mix at 44.1 kHz when it is on, the game's buffers at 22.05 kHz with `--musyx native`; 1.0 is 16-bit full scale) |
| `--dump-output <wav>` | Write everything sent to the audio device, replacement music included, to a WAV file |
| `--dump-dl <file> <seconds>` | Write the first display list submitted after that many seconds, decoded as text (F3DEX2) |
| `--musyx hle\|native\|lle\|compare` | Pick the MusyX implementation (default `hle`, with the high-quality mix unless the Sound tab's MusyX Mixing is Original; `native` is the HLE without it, whatever the Sound tab says) |
| `--watch <hexaddr>` | Watch one RDRAM byte; print every thread's stack on each of its first 6 changes |
| `--hwwatch <hexaddr>` | Put an x86 hardware data breakpoint on one RDRAM byte, so reads are caught too; print the game stack of each new instruction that reads or writes it (the first 63) |
| `--dump-ram <prefix> <t1,t2,..>` | Write all of RDRAM, big-endian, to `<prefix>0.bin`, `<prefix>1.bin`, ... at each of those times in seconds. Diff two dumps to find the byte a setting lives in |
| `--input <file>` | Scripted port 1 input for tests: lines `<seconds> <buttons hex> [x y]` (seconds from the first input read), each held until the next; bit `0x10000` is Rewind |
| `--profile <after> <seconds>` | From `<after>` seconds on, sample every thread each millisecond for `<seconds>` seconds (Windows only), then print each busy thread's share of the samples and its top functions by self and total time, as `[profile]` lines |
| `--players <n>` | Give ports 2..n the same input as port 1, so split screen can be driven with one pad (all four ports always report a controller) |
